# Shared contracts v1 — builder implementation target

These are proposed contracts, not current storage. S1 owns definitions; later owners implement adapters without silently changing semantics. A version change requires migration notes, fixtures, and projection comparison.

## Scope, identities, and classification

All records carry product=`docketstamp`, environment=`local|staging|production`, schemaVersion, and server receivedAt. Payment livemode, Lob mode (`mock|test_api|live`), and CASS mode are independent fields. NODE_ENV is not payment/postal authority. A live charge with simulated fulfillment creates a critical outstanding obligation.

Store UTC instants; UI default timezone America/Chicago, selectable. Requests supply inclusive start and exclusive end UTC plus display timezone, reportVersion, asOf, cohortPolicyVersion and filters. Default overview: last 7 calendar days including today, visibly partial today. Previous-period comparisons use equal elapsed duration; no full-day-to-partial-day comparison. The current report projection supports filters for notice, tier, entry surface, channel, and customer classification; campaign, offer, and device filters are rejected until their projection support is implemented. Operational exceptions default to **all currently open obligations**, visibly independent of acquisition date filter; never hide an older paid notice by selecting this week.

Identities: anonymous visit/session ID; random non-bearer journeyId for a draft; draftRevision; checkoutAttemptId; orderId; Stripe account+mode+PI/charge/refund IDs; Lob account+mode+letter ID; providerEventId; requestId/correlationId; authenticated actor UID or named service principal. Different sessions may join the same journey by a server-verified resume mapping, never by email heuristics or stage token. Do not expose that mapping publicly. No cross-device identification without explicit supported recovery. Missing identity stays unknown.

Server classification: customer, founder, employee, automated_test, comp, free_promo, suspected_bot, unresolved; retain overlapping facts (e.g. founder + live payment) separately from primary reporting class. Mode, approved test accounts, signed internal test marker, comp authorization and observed bot signals are evidence, versioned and auditable. Browser isTest cannot authorize exclusions or financial truth. Email substring guesses are historical heuristics, not verified class. Unknown orders have their own count/value; never silently call them independent customers. Eligible acquisition denominator is observed external human-candidate customer sessions, with unresolved/suspected bot/internal exclusions separately quantified. This is not verified unique people.

## Event envelope and acceptance

`eventId, eventName, eventVersion, product, environment, occurredAt, receivedAt, emitter(client|server|provider), sessionId?, journeyId?, revision?, checkoutAttemptId?, orderId?, providerEventId?, requestId?, correlationId?, noticeId?, tier?, entrySurface?, experienceVersion?, safeProperties, classificationEvidenceRef?`.

Use a random eventId created once per logical event and retained during retries. Server/provider fact IDs derive from provider account+mode+event identity or a documented natural business key, not Date.now. Store create-if-absent receipt and fact in a transaction; conflicting duplicate payloads enter quarantine. Logical completion uniqueness is journey+revision+milestone; payment attempts use attempt ID so retries are visible. Return accepted/duplicate/rejected; sendBeacon queue acceptance is not server acceptance. Bounded client retry queue stores only sanitized envelope, maximum 100 events / 24 hours; overflow is counted. Storage unavailable must not block preparation/payment. Source time >5 minutes in future or >24h old from browser is quarantined for cohort-time use; retain receivedAt and skew reason. Server/provider late evidence remains admissible, with affected partitions restated and lateness disclosed.

Public browser input never creates financial/postal facts. Validate bounded enums, integers and strings, rate limit, record rejection reason counters without raw bodies, and treat claimed order associations as untrusted until joined to server records. No open-ended event name/metadata bag. One sanitizer at browser, ingestion, server outbox, logging, trace, export and ad adapter boundaries.

## Durable money and obligation records

Use existing Firestore, with additive collections: `business_events_v1`, `payment_facts_v1`, `postal_facts_v1`, `dispatch_attempts_v1`, `business_outbox_v1`, `offer_reservations_v1`, `offer_redemptions_v1`, `admin_audit_v1`, `reconciliation_runs_v1`, `report_generations_v1`, `report_partitions_v1`. Reuse existing orders/discounts, add immutable snapshot metadata and private journey mappings. Collection names are the agreed starting contract; do not add a warehouse/queue vendor without a measured limit requiring it.

Money record: currency, integer amountMinor, kind(capture|refund|dispute_debit|dispute_reversal|processor_fee|supplier_charge|supplier_credit), provider IDs, order association, effectiveAt, receivedAt, verification status, evidence reference and correction linkage. Never overwrite original monetary facts; append corrections/reversals. PI alone is not fee authority; use Stripe charge/balance transaction evidence. Refund requested/pending/succeeded/failed is separate; count successful cash movement once. Avoid subtracting both a refund and the same dispute debit as independent loss; reconcile balance transaction IDs. Operational state, customer classification and accounting fact are separate dimensions.

Payment obligation: successful capture or explicit authorized free/comp; frozen document hash/template version, addresses authorized for that snapshot, tier/quote, paidAt/authorizedAt, dispatch status and proof obligations. Financial truth survives postal errors, returns and delivery. The UI does not imply accrued cash equals recognized accounting revenue; accounting recognition remains a founder/accountant policy.

Postal timeline: authorized → queued → submitting → accepted_by_lob → mailed → in_transit → delivered, with returned/canceled/failed/uncertain branches. Delivered and returned can be subsequent legitimate events; use provider source time and explicit transition rules, not simple numeric rank. Older source events append without regressing current state; conflicting same-time facts require review. Delivered scan is not proof of successful legal remedy. Return receipt is a distinct artifact obligation only where purchased and supported. No promised delivery deadline is derived from a template's statutory dates.

All dispatch writers, including comp/free/admin retry, use a single authorization/snapshot/mode/lock adapter. Lock lease expiry triggers reconciliation before resubmission. Preserve Lob's per-order Idempotency-Key. Corrections that alter recipient/letter content create a new signed snapshot/order linkage; never send corrected envelope around a contradictory frozen letter. After provider acceptance, an intentional replacement mailing requires separate explicit authorization, cost preview, and linked new fulfillment identity; it is not a technical retry.

Transactionally persist order/fact and outbox before acknowledging authority event success. Analytics and ad delivery are asynchronous consumers, unable to erase payment or block dispatch. At-least-once processing plus uniqueness/leases, not claims of exactly-once external effects. Record consumer success only on accepted response. Payment validation is common to webhook, browser-confirm backend and admin reconciliation; public browser assertions alone never suffice.

## Metric dictionary

Every response metric has `key, value|null, unit, numerator?, denominator?, evidenceClass(observed|verified|inferred|estimated|unavailable), source, definitionVersion, scope, asOf, watermark, completeness, exclusions, qualityFlags, evidenceQueryRef`. Completeness is complete only within a declared ingested scope/watermark, never the entire internet. “Verified” applies to facts; a conversion computed from observed browser sessions retains observed/partial coverage.

| Metric | Exact calculation and time basis | Evidence/drilldown |
| --- | --- | --- |
| Independent paid orders | Distinct customer-class live captured order IDs with successful verified amount >0, by payment effectiveAt in scope; refunds do not erase original sale. | Payment facts; split unknown-class live captures, free and internal. |
| Net customer collections | Captures minus successful refunds and net dispute debits for customer-class facts, grouped by currency/effective cash date; no FX combining. | Cash movement IDs and pending refund/dispute panel. |
| Eligible sessions | Distinct qualifying observed sessions with entry_viewed in scope; automated staging API calls excluded. | Session rows, classification policy/exclusions; cookie blocking coverage unknown. |
| Observed paid-session conversion | Distinct eligible sessions with a joined verified customer paid order within 7 days after entry / eligible sessions. One converting session counted once regardless of repeat orders. | Evidence joins; immature cohorts labeled pending through day 7; unknown joins separate. Homepage cohort optional filter; direct/stage cohorts included in business overview. |
| Observed progression | For each journey, milestones actually observed and linked. Ordered funnel uses first qualifying event chain with explicit prerequisites and server receivedAt tie-break; independent milestone reach counts displayed separately. | Missing-prerequisite/late/skew buckets. No synthesized stage or capped percentages hiding invalid sequences. |
| No observed continuation | Eligible journey reached milestone but no later qualifying event after 30m inactivity, with 7-day cohort maturity distinct. | Inferred inactivity, never “confirmed abandonment” or guaranteed recoverable revenue. |
| Paid service completion | Customer paid orders with Lob live accepted evidence / customer paid orders in payment cohort, plus mailed and delivered scan counts separately. | Denominator and pending-age distributions; proof availability by tier. Not customer legal outcome. |
| Open obligations | Current authorized paid/free/comp obligations without accepted live dispatch; split unsubmitted, uncertain, blocked, overdue and simulated/live mismatch. | All open rows regardless of selected entry date; class and value shown. |
| Dispatch latency | p50/p95 paidAt→acceptedAt for accepted live mailings, paired with open-obligation ages and numerator n. | Explicit n; no percentile for empty set, no hiding pending failures. |
| Contribution before advertising | Net collections less actual processor fees and actual supplier charges net credits attributable to same order cohort; versioned estimated costs allowed in separate estimated column. | Missing cost count/value; no complete contribution if required component unavailable. Discount already reflected in payable capture, do not subtract twice. |
| Spend / CPA / ROAS | Spend by account+campaign+day+currency+coverage; CPA=aligned attributed paid orders acquisition cost (orders, not unique customers); ROAS=aligned cohort net collections / spend. | Coverage/mapping/time-basis visible. Missing/zero denominator=null. CAC only with verified new-customer identity; otherwise unavailable. Cash-date and acquisition-cohort views never silently mixed. |
| Offer conversion | Unique eligible exposed journeys with committed paid redemption / unique eligible exposed journeys; free redemption separate. | Full exposure→apply→reserve→pay/free→refund/fulfill counts, attribution coverage, no causal lift label. |
| Measurement confidence | Separate dimensions: payment match %, session join %, classified order %, late/duplicate/rejected counts, export acceptance, cost/spend coverage, watermark lag, last successful reconcile. | Counts and reasons, not a blended trust score concealing weakness. |

## Attribution, privacy and reconciliation

Persist immutable original acquisition touch plus latest qualified acquisition touch, product entry surface, later offer/recovery touches and consent state separately. Proposed attribution window: 30 days, configurable/versioned; session conversion maturation stays 7 days. A new promo touch does not overwrite original acquisition. Campaign key includes platform/account/source/medium/campaign ID; display names are not keys. Unknown, direct, organic and unattributed paid are separate. Client metadata is observational; sanitize/validate campaign identifiers and link server order snapshot to the captured version. Capture privacy signals even without campaign tags; apply current opt-out on later ad export. Internal reporting and ad-platform reported conversions are explicitly different authorities.

No names, addresses, DOB, SSN fragments, balances, document text/signatures, unrestricted recipient text, search, raw URLs/queries, stage/view tokens, payment secrets, emails or raw errors in analytics/traces/ad payloads. Use route templates including `/order/:id` rather than real IDs; avoid notice-specific dispute/biometric categories in ad egress. First-party restricted investigation may use notice dimensions with role checks; sensitive letter preview stays in protected detail. Hashing identifiers does not make ad export harmless. Generic purchase-only payload subject to approved privacy policy; do not export test/employee/founder/free as paid customer purchases. Sanitize storage and console outputs, not only browser metadata. Exports redact identifiers by default, use authorization, audit, formula-injection-safe CSV and bounded downloads. Do not place private customer filters in shareable URLs.

Reconcile incrementally with provider event IDs and cursors; proposed schedule every 15m for recent payment mismatches, hourly for open postal obligations, daily for fees/costs/refunds/spend where credentials and sources exist. These are proposed operating targets, not supplier guarantees. Overlap checkpoints by 48h; late provider events restate affected partitions. Full bounded date replay on demand. Runs record start/end, provider scope, cursor, scanned/matched/unmatched/conflicting totals, errors and watermark. Quarantine unmatched events and missing-order captures; acknowledge only after durable receipt. Never silently discard an unknown order to keep a webhook green.

Replay mode is `projection_only` by default: dry-run counts/hash first, then writes into a new report generation. It cannot dispatch, charge/refund, email, or export to ads. Rebuild per time partition with transaction/create-if-absent event receipts; no ever-growing singleton dedupe arrays. Publish generation atomically only after expected totals and sampled evidence match; retain previous generation and cursors for rollback. Reconciliation of financial/postal facts never initiates fulfillment. External execution is a separate audited operator command.
