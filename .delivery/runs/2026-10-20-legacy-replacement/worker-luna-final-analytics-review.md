# Final cross-lane review: analytics/admin reporting

Review scope: coordinator checkout `/Users/zeke/code/DocketStamp`, analytics/admin/reporting and marketing integration at `453034cb37d64a5f2452cfd5613522d4a264475d`. I authored the orders implementation and excluded that work from independent review. This is a read-only review; no external destinations or cloud services were contacted.

## Actionable findings

- **P1 — the server accepts a client-controlled marketing consent grant.** `app/api/docket/lock-and-intent/route.ts:39-40,261-265` accepts `marketingConsent` from arbitrary JSON and persists `true` without independent consent evidence. The route is unauthenticated for notice creation and takes `customerEmail`/sender data from the same request; a direct caller can set `marketingConsent: true`, pay, and cause `lib/meta-conversions-api.ts:313-347` to hash and send those identifiers to Meta. Checkout's normal client calls `hasExplicitMarketingConsent()`, but that is not a server trust boundary. Bind consent to a verifiable first-party grant (and honor `Sec-GPC: 1` server-side), or keep server CAPI disabled until such proof exists. Also, `docketstamp_marketing_consent_v1` has no writer in the shipped UI, so there is currently no supported customer path to grant it.

- **P2 — accepted report scope filters can silently be ignored.** `ScopeSchema` advertises `campaignKey`, `offerId`, and `device` (`lib/admin-console/contracts/index.ts:48-52`); `/api/admin/console` accepts that schema and keys/publishes reports by the full scope (`app/api/admin/console/route.ts:13-16,23-35`, `lib/admin-console/reporting/store.ts:6,25-43`). `computeReport` never applies those three filters (`lib/admin-console/reporting/compute.ts:41-69`). A caller can therefore request a campaign/device/offer-specific generation and receive aggregate metrics labeled with that narrower scope. Implement them or reject them until supported.

- **P2 — CAPI failures are permanently marked as tracked.** `lib/order-processor.ts:529-541` ignores the `MetaCapiResult` and writes `metaCapiTrackedAt` after any resolved call, including the explicit skipped/rejected results returned by `sendMetaCapiPurchaseEvent` (`lib/meta-conversions-api.ts:313-325,374-380`). A transient Meta rejection or currently disabled destination therefore prevents a later retry for that order. Only mark successful delivery, or persist retryable outbox state with the existing `order.id` event ID.

- **P2 — the Meta test-event code is global rather than environment-scoped.** `getMetaTestEventCode()` reads one `META_TEST_EVENT_CODE` for all environments (`lib/meta-conversions-api.ts:26-28`), and `sendMetaCapiEvents` attaches it to every event (`:182,253-259`), including live production purchases. If the verification code remains configured after testing, production conversions are routed to the test-event stream. Scope the code to local/staging or require a test-only explicit override.
